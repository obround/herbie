When defining a platform, every representation and operation must have an associated cost. This cost helps Herbie decide between multiple accurate programs, guiding it towards the one that will run the fastest on the target platform.

How to Calculate Costs

The process involves benchmarking each operation within a hot loop, measuring its execution time, and then normalizing these timings against a baseline to determine relative costs. We need to determine two kinds of costs:

  1. Representation Costs: The cost of reading a value of a particular representation from memory. We can measure this by benchmarking the identity function (does nothing but return its input) over each representation. This gives us a baseline move cost for each representation like <binary64> or <bool>.
  2. Operation Cost: The cost of executing a specific floating-point operation, like + or sin. We measure this by benchmarking the operation itself.

Once these timings have been determined, the final step is to normalize them. Usually, normalizing against the cheapest operation (often the boolean move cost) by calling its cost 1 is a practical approach. In general, as long as you have cost values that more or less represent the relative difference in timing between operations (e.g., the costs show that + is significantly cheaper than cos and about the same as -), you should be fine. Nevertheless, you must be careful when profiling.

Reliable Profiling

Modern computers and runtimes have many complex systems that can complicate getting accurate measurements. Here are a few key things to watch out for.

Compiler Optimizations

Modern compilers attempt to optimize executables to be the fastest they can possibly be without affecting the program's final result. This section applies primarily to AOT and JIT compilers. Here are two optimizations to look out for:

Dead code elimination is an optimization where the compiler can delete a function call entirely. This can happen when you benchmark a function but never use its result. For example, if you had a for loop that simply added two numbers without using the result, the compiler might delete this block of code entirely as it has no effect on the program's final behavior. To fix this, you must ensure that the result of your benchmarked operation is always used in a way that the compiler can't ignore it. One way to ensure that the result of a benchmarked optimization is always used is by having a "sink variable" to which you can add the result of each operation. This ensures that each operation has a side-effect without influencing the relative costs.

Constant folding is an optimization where expressions with constant inputs (e.g. cos(0.0)) is replaced with the evaluated result at compile-time (1.0). To fix this, always benchmark with inputs that are not known at compile time.

Computer and Runtime

Cache effects can drastically affect a piece of code's performance, especially when using JIT compilation. The first time a piece of code is run may be slower because the compiler has to translate to machine code. This is called a cold start. However, subsequent runs may be much faster because the compiled code is cached (and often optimized). The fix is to always include a warmup phase in the benchmark where the hot loop is run a couple of times to ensure the caches/optimizations are ready before actual benchmarking. Discard the results from the warmup phase.

Background noise from the computer and runtime, including garbage collection, system updates, and other background processes, can interrupt the benchmark and results. Try to ensure you have a "quiet" machine and that the garbage collector runs predictably and doesn't affect the final measurement.

Vectorized calculations can be necessary for reliable measurements. Consider a Python library such as Numpy. A naive benchmark over scalar values will produce a misleading result where every operation takes approximately the same time. This is because the Python interpreter and the overhead of calling the C++ backend will end up dominating the measurement. Therefore, to get meaningful performance measurements, benchmarks for a library such as Numpy must be performed over vectors rather than scalars. This allows the thousands or millions of operations to dominate the fixed cost, revealing the true performance of the operations.

Being Scientific

After warming up, benchmark each operation for many iterations, and take the minimum timing of all the iterations (assuming all the timings are just about the same).

Final Notes

  • The relative costs don't have to be perfectly accurate to be effective: as long as they capture the general trend, they can make a significant difference in performance on the target platform
  • Sanity check costs along the way: make sure functions such as exp cost much more than +, functions like pow have very high costs, etc.
  • Greater cost granularity is good as it often implies greater accuracy (e.g., costs as integers distributed over 1 to 30 vs 1 to 15)
